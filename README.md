# Exchange Simulator

Web-система имитационного моделирования биржевой торговли
для тестирования торговых стратегий.

## Структура

- `backend` — серверная часть на FastAPI;
- `frontend` — клиентская часть на React и Vite;
- `compose.yaml` — локальный PostgreSQL;
- `backend/migrations` — миграции базы данных Alembic.

## Локальный запуск

### Требования

- Python 3;
- Node.js и npm;
- Docker с поддержкой Docker Compose.

Все команды ниже выполняются из корня проекта.

### 1. Создать `.env`

Скопируйте пример конфигурации:

```bash
cp .env.example .env
```

В PowerShell используйте:

```powershell
Copy-Item .env.example .env
```

При необходимости измените логин, пароль и другие значения в `.env`. Значения
`POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` должны соответствовать строке
подключения `DATABASE_URL`. По умолчанию PostgreSQL доступен на порту `5433`.

### 2. Запустить PostgreSQL

```bash
docker compose up -d db
```

Проверить состояние контейнера можно командой:

```bash
docker compose ps
```

### 3. Создать Python-окружение и установить зависимости

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
```

Windows PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements.txt
```

### 4. Применить миграции

С активированным виртуальным окружением выполните:

```bash
python -m alembic upgrade head
```

Загрузить воспроизводимый демонстрационный справочник рынка с активами BTC, ETH,
USD и инструментами BTC/USD, ETH/USD:

```powershell
python -m backend.scripts.seed_market
```

Команду можно запускать повторно — дубликаты не создаются.

### 5. Установить зависимости frontend

```bash
cd frontend
npm install
cd ..
```

### 6. Одновременно запустить backend и frontend

Откройте два терминала в корне проекта. В первом активируйте `.venv` и запустите
backend:

```bash
python -m uvicorn backend.app.main:app --reload
```

Во втором запустите frontend:

```bash
npm --prefix frontend run dev
```

После запуска доступны:

- frontend: <http://localhost:5173>;
- backend: <http://localhost:8000>;
- проверка backend: <http://localhost:8000/health>;
- Swagger UI: <http://localhost:8000/docs>.

## Просмотр содержимого базы данных

PostgreSQL работает внутри контейнера `db`. Чтобы открыть интерактивную консоль
`psql`, выполните из корня проекта:

```powershell
docker compose exec db psql -U exchange_user -d exchange_simulator
```

Если значения `POSTGRES_USER` или `POSTGRES_DB` были изменены в `.env`, замените
`exchange_user` и `exchange_simulator` в команде на свои значения.

Основные команды внутри `psql`:

```sql
-- Показать таблицы базы данных
\dt

-- Показать структуру таблицы пользователей
\d users

-- Показать виртуальные активы
SELECT id, symbol, name, is_active FROM assets ORDER BY symbol;

-- Показать торговые инструменты
SELECT
    instruments.id,
    base.symbol || '/' || quote.symbol AS symbol,
    instruments.is_active
FROM instruments
JOIN assets AS base ON base.id = instruments.base_asset_id
JOIN assets AS quote ON quote.id = instruments.quote_asset_id
ORDER BY instruments.id;

-- Показать сохранённые эксперименты
SELECT id, owner_id, name, duration_steps, seed, updated_at
FROM simulations
ORDER BY id;

-- Показать пользователей без хэшей паролей
SELECT id, email, role, is_active, created_at
FROM users
ORDER BY id;

-- Показать применённую версию миграций Alembic
SELECT * FROM alembic_version;

-- Выйти из psql
\q
```

Отдельный запрос можно выполнить без входа в интерактивную консоль:

```powershell
docker compose exec db psql -U exchange_user -d exchange_simulator -c "SELECT id, email, role, is_active, created_at FROM users ORDER BY id;"
```

## Роли пользователей

После обновления кода примените новую миграцию:

```powershell
python -m alembic upgrade head
```

Новые пользователи получают роль `user`. Для назначения первого администратора
зарегистрируйте пользователя обычным способом, затем из корня проекта выполните
на сервере с доступом к базе данных:

```powershell
python -m backend.scripts.promote_admin admin@example.com
```

Подставьте email зарегистрированного пользователя. Дальше администратор может
менять роли через `PUT /api/users/{id}/role` с Bearer-токеном и телом
`{"role": "user"}` или `{"role": "admin"}`. Роль также возвращается в
`GET /api/auth/me`. Без действительного токена сервер отвечает `401`, а
пользователю без роли администратора возвращает `403`.

## Возможности первого этапа

После регистрации и входа пользователь может через web-интерфейс:

- просмотреть доступные торговые инструменты;
- создать конфигурацию эксперимента с одним или двумя инструментами;
- задать продолжительность, seed, начальные цены, балансы и объёмы заявок;
- добавить несколько фоновых профилей Random и Trend Following;
- отдельно настроить тестируемую стратегию;
- сохранить, повторно открыть и изменить свою конфигурацию.

Пользователь не может открыть конфигурацию другого пользователя. Администратору
доступны управление ролями, виртуальными активами и торговыми инструментами.

Основные маршруты конфигураций:

```text
GET  /api/assets
GET  /api/instruments
POST /api/simulations
GET  /api/simulations
GET  /api/simulations/{id}
PUT  /api/simulations/{id}
```

Создание и изменение активов и инструментов выполняется администратором через
`POST` и `PUT` маршруты `/api/assets` и `/api/instruments`.

## Торговый механизм второго этапа

Модели `Order` и `Trade` и сервис `backend/app/services/trading.py` добавляют
лимитные заявки BUY/SELL, резервирование, сопоставление и расчёт балансов.
Стакан разделён по запуску и инструменту. Сначала исполняется лучшая цена,
при равных ценах — заявка с меньшим `sequence_number`. Цена сделки равна
цене уже стоящей в стакане заявки. Сделки участника с самим собой пропускаются.

`place_order()` сохраняет отклонённую заявку при нехватке доступных средств.
`cancel_order()` освобождает только оставшийся резерв; повторная отмена не
меняет баланс. `get_order_book()` возвращает активные заявки, а
`get_price_history()` — цены сделок в порядке исполнения, без начальной цены.

Цены и объёмы имеют до 8 знаков после запятой. Денежный резерв округляется
вверх, сумма расчёта сделки — вниз до 8 знаков. Разница возвращается покупателю.
Стоимость заявки должна быть не меньше `0.00000001`; остаток, который нельзя
исполнить в пределах этой точности, остаётся в стакане до отмены.

Сервис выполняет `flush`, но не `commit`: вызывающий код должен завершить всю
операцию одной транзакцией и откатить её при ошибке. Запись в пределах одного
запуска сериализуется блокировкой строки `SimulationRun` в PostgreSQL.
Сервис внутренний; проверка владельца должна выполняться вызывающим API.
Полный цикл и API реализованы следующим блоком. Интерфейс мониторинга
стакана и результатов доступен на экране запуска.

После обновления примените миграции:

```powershell
python -m alembic upgrade head
```

Тесты торговых правил и стратегий (SQLite в памяти, без изменения рабочей БД):

```powershell
python -m unittest discover -s backend/tests -v
```

## Выполнение симуляции

При запуске FastAPI автоматически стартует фоновый обработчик. После
`POST /api/simulations/{id}/start` он выполняет шаги сохранённой конфигурации.
Один модельный интервал равен одному шагу: на каждом шаге участники принимают
решения в порядке `sequence_number`, инструменты — в порядке их ID.
Каждое решение сразу передаётся торговому механизму; последующий участник
видит новые сделки и цены. Начальная цена используется Random до первой сделки,
но не считается сделкой в окне Trend Following.

Один шаг, заявки, сделки, балансы, прогресс и состояние RNG сохраняются одной
транзакцией. PostgreSQL блокирует строку запуска, поэтому два обработчика не
могут выполнить его шаг одновременно. После перезапуска backend незавершённые
запуски продолжаются с последнего сохранённого шага. При штатном выключении
обработчик завершает текущий шаг. При ошибке шага он откатывается, запуск
получает статус `failed`, сообщение ошибки и освобождает оставшиеся резервы.
Подробности исключения находятся в серверном журнале.

Остановка ждёт окончания текущей транзакции шага, устанавливает `stopped`
и отменяет оставшиеся заявки. Завершение всех шагов устанавливает `completed`
и тоже освобождает резервы. Версия движка теперь `2`: старые незавершённые
запуски версии `1` получают статус `failed`; их конфигурацию можно запустить заново.

API текущего состояния (доступно только владельцу эксперимента):

```text
GET  /api/simulations/{id}/run
POST /api/simulations/{id}/start
POST /api/simulations/{id}/stop
GET  /api/simulations/{id}/order-book?instrument_id=1&limit=50
GET  /api/simulations/{id}/orders?after=0&limit=100
GET  /api/simulations/{id}/trades?instrument_id=1&after=0&limit=100
GET  /api/simulations/{id}/balances?after=0&limit=100
GET  /api/simulations/{id}/results
```

Стакан, история, балансы и результаты по умолчанию относятся к последнему
запуску; `?run_id=...` позволяет получить предыдущий запуск. Если запуска нет,
возвращается `404`. Для истории `after` — номер последней полученной заявки
или сделки (`sequence_number`), для балансов — порядковый номер участника.
`limit` ограничен диапазоном 1–1000. Стакан возвращает до `limit` заявок с
каждой стороны. Повторный опрос статуса можно выполнять примерно раз в секунду.

Результат рассчитывается из сохранённых балансов и последних цен:
котируемый баланс плюс стоимость базовых активов. Учитываются доступные и
зарезервированные средства. Начальная стоимость берётся из снимка запуска;
прибыль равна разнице текущей и начальной стоимости, доходность — их отношению
в процентах. При нулевой начальной стоимости доходность возвращается как `null`.
Также возвращаются общее число сделок и число сделок тестируемого участника.
Пока запуск выполняется, эти показатели являются промежуточными.

После обновления выполните `python -m alembic upgrade head` перед запуском backend.
HTTP-тесты используют SQLite в памяти и настоящий ASGI API с JWT; рабочая БД
при запуске тестов не меняется. Многопроцессные блокировки требуют PostgreSQL.

## Мониторинг через web-интерфейс

Кнопка «Запустить» открывает экран конкретного запуска. Кнопка «Мониторинг и
результаты» возвращает к последнему запуску сохранённого эксперимента.
Экран показывает прогресс, стоимость портфеля, прибыль, доходность, число
сделок, баланс тестируемого участника, стакан, историю заявок и сделок,
а также балансы фоновых участников. Для двух инструментов используется
переключатель торговой пары. Данные обновляются примерно раз в секунду
до завершения запуска. После завершения выполняется итоговое обновление.

История и участники разбиты на страницы по 50 записей; стакан показывает
до 20 лучших заявок с каждой стороны. При ошибке запроса последние данные
остаются на экране с предупреждением и кнопкой повтора. Уход с экрана отменяет
его запросы и таймеры, но не останавливает серверную симуляцию.

Для мониторинга используются инструменты самого запуска, а не текущего
шаблона. Остановка передаёт `run_id`, поэтому старая вкладка не может случайно
остановить более новый запуск. Изменений структуры БД в этом блоке нет;
обновить и перезапустить нужно обе части приложения.

### Быстрый запуск после обновления в Windows

Откройте Docker Desktop. В первом PowerShell-терминале выполните из корня
репозитория следующие команды. Существующий `.env` сохраняйте; копировать
`.env.example` нужно только при первом запуске.

```powershell
cd C:\Users\arthur\PROG\trade
docker compose up -d db
docker compose ps
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m backend.scripts.seed_market
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload
```

У контейнера `db` должно быть состояние `healthy`. Если оно ещё `starting`,
повторите `docker compose ps` через несколько секунд и только затем запускайте
миграции. Если `.venv` отсутствует, сначала создайте окружение и установите
зависимости по разделу «Локальный запуск» выше.

Во втором PowerShell-терминале:

```powershell
cd C:\Users\arthur\PROG\trade
npm --prefix frontend install
npm --prefix frontend run dev
```

Откройте `http://localhost:5173`. Если Vite указал другой порт, используйте
адрес из его вывода. Backend должен оставаться запущенным в первом терминале.

### Ручная проверка второго этапа

1. Войдите или зарегистрируйтесь. После `seed_market` доступны BTC/USD и ETH/USD;
   права администратора для создания эксперимента не нужны.
2. Создайте эксперимент: 100 шагов, seed 42, BTC/USD, начальная цена 60000,
   котируемый баланс фонового и тестируемого участника 100000 USD, по 10 BTC,
   объём заявки от 0.01 до 0.1.
3. Добавьте фоновый профиль Random с 10 участниками, вероятностями BUY 45%,
   SELL 45%, HOLD 10% и отклонением цены 1%. Для тестируемой стратегии задайте
   такие же параметры. Сохраните и нажмите «Запустить».
4. Убедитесь, что шаги растут без перезагрузки страницы, появляются заявки
   и сделки, а после всех шагов статус меняется на «Завершён». Итоговый
   стакан будет пустым: оставшиеся заявки отменяются при завершении.
5. Во время выполнения просмотрите стакан. В истории заявок проверяйте статусы
   и остатки; при нехватке средств заявка отклоняется. Если записей больше 50,
   проверьте кнопки «Далее» и «Назад».
6. Вернитесь к экспериментам, измените продолжительность на 1000 шагов,
   сохраните и запустите заново. Нажмите «Остановить запуск». Должен появиться
   статус «Остановлен», а резервы после обновления должны стать нулевыми.
7. Добавьте ETH/USD с начальной ценой 3000 и начальным базовым балансом,
   сохраните и запустите. Переключайте пару и проверяйте отдельные стаканы
   и историю. В обоих инструментах котируемый актив — USD.
8. Повторите завершённую конфигурацию без изменений. При одинаковых seed
   и версии движка должны совпасть торговые действия, цены, объёмы и результат.
   ID строк и время запуска могут отличаться.
9. Обновите страницу: завершённый результат должен остаться доступным.
   Если выбрана только Trend Following и сделок ещё нет, участники могут
   выполнять HOLD до конца — это нормальное поведение. Для её проверки
   оставьте на фоне Random.

## Основные HTTP-коды

- `201` — ресурс успешно создан;
- `401` — не удалось подтвердить личность: неправильный пароль, неактивный
  пользователь, отсутствующий или просроченный JWT;
- `403` — личность подтверждена, но не хватает прав;
- `404` — запрошенный ресурс не найден или не принадлежит пользователю;
- `409` — ресурс с таким уникальным значением уже существует;
- `422` — данные не прошли проверку.
